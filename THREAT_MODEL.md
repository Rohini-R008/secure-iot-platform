# Threat Model

| Asset | Attacker | Attack | Impact | Mitigation (implemented) |
|---|---|---|---|---|
| Telemetry integrity | Anyone on the network | **Spoofed sensor** — connect and publish fake readings with no/forged identity | Poisoned data, false readings drive bad decisions | Mutual TLS with per-device X.509 certs; broker requires a CA-signed client cert (`require_certificate`), so anonymous clients are refused. Processor also rejects payloads whose `device_id` ≠ topic identity. |
| Per-device isolation | Compromised device | **Cross-device impersonation** — a real device publishes to another device's topic | One breached sensor forges the whole fleet | Per-device ACL (`pattern readwrite devices/%u/#`) confines each cert identity to its own topic subtree; cross-topic publishes are denied and logged. |
| Data pipeline | Malicious publisher | **Malformed / injection** — bad JSON, wrong types, impossible values | Crash processing, corrupt storage, hide real signals | Strict validation (schema, types, physical ranges) in the processor; rejected messages are logged to a queryable audit trail, never silently dropped. |
| Credential lifecycle | Attacker with a stolen device key | **Stolen credential** — reuse a leaked/exfiltrated device certificate | Persistent unauthorized access | Certificate Revocation List (CRL) enforced by the broker; admin can revoke a device via the UI and it is locked out on reconnect in real time. |
| Availability | Any client | **DoS / flooding** — high-volume connects or publishes | Broker overload, dropped legitimate traffic | TLS + auth raise the cost of connecting (no anonymous flood); ACL limits topic scope; per-device identity enables targeted revocation of an abusive device. (Rate-limiting noted as future work.) |
| Firmware / config integrity | Insider or MITM | **Malicious firmware/config push** — send rogue commands to devices | Attacker controls devices | Command topics would be under the same per-device ACL + mTLS; only authenticated, authorized identities can publish, and all actions are audited. (Signed-firmware verification noted as future work.) |
| Access control | Curious/insider operator | **Privilege escalation** — operator attempts an admin-only action (revoke) | Unauthorized credential revocation | RBAC enforced server-side (`require_admin`); operators cannot revoke even by crafting the request, and forbidden attempts are audited as `forbidden_access`. |
| Auditability | Any actor | **Repudiation** — deny having done an action | No accountability, can't investigate | Every login, access attempt, config change, and revocation is written to a dedicated append-only audit store (queryable in InfluxDB + Grafana). |
